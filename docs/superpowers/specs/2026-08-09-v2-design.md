# rag-lab V2 — Design

**Datum:** 2026-08-09
**Status:** Entwurf (Review durch User offen)
**Basis:** V4-Phase-A-Stand (Audit-Fixes B1–B6, A1–A4, O1–O5, T1–T3; 105 Tests grün)

## 1. Ziel

V2 macht rag-lab von einem "funktioniert für Markdown/PDF-Korpus" zu einem
Werkzeug für den echten Uni-Alltag: gescannte PDFs und PPTX werden abgedeckt,
der Korpus kann inkrementell synchronisiert werden, die Retrieval-Qualität wird
eval-getrieben verbessert, die API wird gehärtet, und Workspaces trennen
Studium von Privatem.

**Vom User entschieden:**
- Scope: alle vier Bereiche (Corpus-Reality, Retrieval-Qualität, Betrieb & Sicherheit, Tägliche Nutzung)
- V4-Index mit Re-Baseline erlaubt (neue Collection, alte bleibt)
- LLM-Stack bleibt OpenRouter-only (kein Ollama)
- Definition of Done: eval-gesteuert
- Arbeit wird pro Phase committet; der Session-Zwischenstand ist der erste Commit
- **Kein Streaming in V2** (SSE als V2.x danach)
- Refinement v2 = **Zusatz-Retrieval-Runde** (kein LLM-Query-Rewrite)

## 2. Definition of Done (gesamt)

- Jede Phase schließt grün: `uv run pytest` + `ruff check --select E9,F` + `scripts/check.sh` (Retrieval-Gate)
- Golden Set ≥ 50 Fragen; V4-Baseline dokumentiert und ≥ V3-Baseline (hit@k gleich oder besser, chunk-Metriken besser)
- `documentation.md` + `README.md` spiegeln jede Phase wider (TASKS.md-Regel)
- Alte v3-Collection bleibt unangetastet erhalten; Re-Baseline ist dokumentiert

## 3. Phasen

### Phase 0 — Sofort-Härtung (S)

1. **`0.0.0.0`-Fix** — `config.py:82`: `"0.0.0.0"` aus `is_loopback_host`-Menge entfernen.
   `rag serve --host 0.0.0.0` ohne `RAG_API_TOKEN` verweigert mit Exit 1 (fail-closed).
   Tests: `is_loopback_host("0.0.0.0") is False`; serve-Verweigerung.
2. **Constant-time Token-Vergleich** — `web.py:34`: `hmac.compare_digest` statt `!=`.
   Bestehende 401-Tests decken das Verhalten ab.
3. **Keyword-Limit-Fix** — `retriever.py:224`: `keyword_search(cfg.keyword, limit=cfg.rerank_top)`
   → `limit=cfg.top_k` (50 statt 5). Doku-Klausel "Exhaustive enumeration" wird damit wahr.
   Test: 7 Matches → alle 7 in den Chunks verfügbar.
4. **Session-Zwischenstand committen** — 25 Dateien der Audit-Session als erster Commit
   auf neuem Branch `v2` (Arbeitsstand ist grün).

### Phase 1 — Corpus-Reality (M/L)

1. **A.2 OCR-Fallback**
   - Optionaler dep-Group `[ocr]` (`uv sync --group ocr`), Doku: `brew install tesseract tesseract-lang`
   - PDF-Parser: nur Low-Yield-Seiten (A.1-Flag, `avg < 50 chars/page`) werden OCR'd; gute Text-Layers nie
   - OCR-Cache keyed by `file_sha`, abgelegt neben dem Manifest (Re-Ingest muss billig bleiben)
   - Flags `--ocr/--no-ocr`; Auto-On wenn Engine installiert; klarer Fehler mit Install-Anleitung sonst
   - `RAG_OCR_LANGS` default `deu+eng`
   - Tests: Mini-Scan-PDF-Fixture → OCR-Pfad liefert Chunks; Cache-Hit-Test; `--no-ocr` verhält sich wie heute
2. **A.4 PPTX-Parser**
   - `python-pptx` Dependency; `parsers/pptx.py`: alle Textframes pro Slide + Speaker Notes; Slide = Section
   - Citation: `lecture03.pptx slide 12`
   - Register `.pptx` in `PARSERS` (Dashboard/MCP erben automatisch, wie bei DOCX)
   - Tests + Fixture (Titel, Bullets, Notes)
3. **B.2 `rag sync`**
   - `rag sync <dir>... [--prune] [--dry-run]`: rekursiver Scan nach unterstützten Extensionen
   - Skip bei unverändertem SHA (Manifest), Re-Ingest bei Änderung
   - `--prune`: löscht indexed docs deren Quelle weg ist (Bestätigung außer `--yes`)
   - Summary-Tabelle: added / updated / unchanged / pruned / failed (mit Parse-Qualitäts-Warnungen)
   - Kein `--watch` (Parking lot)
   - Tests: unchanged-skip, changed-reingest, prune, dry-run
4. **A.5 Eval-Wachstum Teil 1**
   - DOCX- und PPTX-Beispiele in `data/`; 8–10 neue Fragen (inkl. eine Slide-Notes-Frage) in `eval/questions.yaml`
   - Baseline auf v3 gemessen (Referenz für Phase 2)

### Phase 2 — Retrieval-Qualität (L)

1. **V4-Index**: `INDEX_VERSION="v4"` → neue Collection `rag_lab_v4-…`;
   v3-Collection bleibt; voller Re-Baseline (`rag rebuild`)
2. **Embedding-Vergleich als Messung**: gleicher Golden Set, drei Kandidaten
   (E5-small = Baseline, E5-large, bge-m3), ein Vergleichs-Lauf, Gewinner wird V4-Fingerprint.
   Reranker bleibt mmarco (späteres Experiment möglich, kein Matrix-Sweep jetzt)
3. **Refinement v2 — Zusatz-Retrieval**: bei PARTIAL werden Suchbegriffe aus den
   Verifier-Issues extrahiert → gezielte Zusatz-Retrieval-Runde → Re-Generierung mit
   mehr Kontext. Kein Extra-LLM-Call fürs Refinement selbst. `max_iters` bleibt 3.
   Messbar an `verifier_mean`/`fragment_rate`; Tests: Mock-Verifier mit Issues → Zusatz-Runde ausgelöst
4. **Verifier-Prompt v2**: claim-weise Issues + erwartete Zitationslabels mitgegeben
   → bessere Refinement-Eingaben, messbar an `citation_validity_rate`
5. **Golden Set 23→~50**: + Deutsch-Uni-Fragen, + Refusals, + nahe Distraktoren.
   Gates nach V4-Messung nachziehen (z.B. `hit_at_3`, `context_chunk_hit_rate`)

### Phase 3 — Betrieb & Sicherheit (M)

1. **Rate-Limits**: eigener In-Memory-Token-Bucket (~40 Zeilen, keine neue Dependency)
   auf `/api/query`, `/api/eval`, `/api/ingest`; Defaults konfigurierbar
   (`RAG_RATE_LIMIT_*`). Test: N+1. Request → 429
2. **`rag backup [--output dir]`**: Online-sichere Kopie (SQLite-Backup-API) des
   persist-Dirs (Chroma + `runs.sqlite3`), Datumsstempel; Restore-Anleitung in docs.
   Test: Ingest → backup → mutate → restore → `count()` gleich
3. **Logging**: Request-Log in `web.py` (Methode, Pfad, Status, Dauer) + Auth-Fail-Events,
   ohne Secrets
4. **Dashboard-Audit**: Sicherheits-Review der React-App (Token-Handling, XSS, fetch-Fehlerpfade) + Fixes

### Phase 4 — Tägliche Nutzung (M/L)

1. **B.1 Workspaces (leichtgewichtig)**: `~/.config/rag-lab/workspaces.toml`;
   `rag workspace list/create/use/show`; Collection-Namen `uni_v4-…` / `personal_v4-…`;
   CLI, Web-API und MCP respektieren das aktive Workspace; Web-Settings zeigt es.
   Tests: Auflösungsreihenfolge, Collection-Mapping, Cross-Workspace-Isolation
2. **B.3 MCP-Polish**: Tool-Beschreibungen (search vs answer vs keyword, LLM-klar),
   Error-Ergonomie (leere Collection, fehlender Key → verständliche Meldung),
   README-Registrierungs-Snippets (Claude Code / Claude Desktop)
3. **Re-Baseline + Doku**: V4-Baseline in README-Metriktabelle, Gate-Werte final

## 4. Nicht-Ziele (bewusst raus)

- Streaming/SSE (V2.x)
- LLM-Query-Rewrite (Refinement-Mechanismus ist Zusatz-Retrieval)
- Lokales LLM / Ollama-Fallback
- `rag sync --watch`
- C.2 Metadata-Filtering (braucht eine scheiternde Eval-Frage als Begründung)
- C.1 `rag runs promote` (Golden-Set-Wachstum manuell; Tooling nur bei Bedarf)
- Hyperparameter-Sweep über Reranker-Kandidaten

## 5. Risiken & Annahmen

- **E5-large/bge-m3 RAM & Laufzeit** auf CPU-Mac: Messung pro Kandidat ~1 h; wenn einer
  nicht praktikabel ist, fällt er raus — Messung entscheidet
- **ocrmypdf-Installation**: `brew install` nötig; OCR bleibt optional, Projekt läuft ohne
- **Tesseract-Sprachpakete**: deu+eng Default; fehlende Pakete → klare Fehlermeldung
- **Re-Baseline-Zeit**: 4k Chunks sind Minuten; größere Korpusse linear
- **Token-Kosten Phase 2**: ~50 Fragen × bis zu 2 LLM-Runden = ~100 Calls — vertretbar
- **Workspace-Migration**: bestehende v4-Collection wird `default`-Workspace zugeordnet;
  keine Datenkopie
- **Alle 25 Session-Dateien sind uncommitted**: erster Commit sichert den Stand; kein
  Risiko für V2-Start

## 7. Git-Strategie

- Neuer Branch `v2` ab `v4-phase-a`
- Commit 1: Session-Zwischenstand (Audit-Fixes, 25 Dateien)
- Commit 2: diese Spec
- Ab dann pro Phase ein Feature-Branch (`v2-phase-N`) → Merge in `v2`, grün als Bedingung
- Conventional-Commits + Co-Authored-By (Projektkonvention)
